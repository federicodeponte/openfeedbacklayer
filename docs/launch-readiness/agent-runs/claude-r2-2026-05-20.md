## NEW Findings (Severity-Ordered)

### P0 (process / deployment) — RESOLVED DURING TEST

**P0-NEW — Live server was serving stale HTML / broken chunks at test start.**
The running `next-server` (pid 2162720, uptime ~10 min) was returning HTML that referenced `/_next/static/chunks/app/layout-1a5e821e942d9a7f.js` → 400 Bad Request. On-disk hash was `layout-ed23a64fb66c160d.js`. React did not hydrate; the FAB rendered statically and clicks did nothing. Without the rebuild + restart I performed (`rm -rf .next && next build && next start -p 3025 -H 0.0.0.0`), every "fix" in this round would have been silently un-verifiable on the live URL. **Operational lesson:** any time you push widget fixes, the example demo needs a `next build && next start` redeploy too — `next dev` chunk caching plus a stale-process restart will silently keep showing pre-fix HTML.
Evidence: `/tmp/ofl-public-start.log`, `curl -sI http://65.21.90.216:3025/_next/static/chunks/app/layout-1a5e821e942d9a7f.js` returned 400 with `text/html` body before rebuild; same chunk URL no longer referenced after rebuild.

### P2 (nice to have)

**P2-NEW-1 — Geist font still 404, just silently this time.**
`GET /__nextjs_font/geist-latin.woff2 → 404`. Was 403 in R1. Either:
(a) remove the Next/font import from the layout entirely (the example sets system-ui inline anyway, so Geist isn't actually used), or
(b) restore the Geist asset so the network layer is clean.
Right now the request is firing on every page load but rendering is unaffected because the inline `<body style="font-family: system-ui, ...">` wins. Cosmetic only; no user-visible regression.

**P2-NEW-2 — Email input missing `autocomplete="email"`.**
After the happy-path submit, Chrome's a11y issues panel logged "An element doesn't have an autocomplete attribute" (count: 1). The email `<input type="email">` should set `autocomplete="email"` so password managers and mobile keyboards behave correctly. One-line fix in `FeedbackWidget.tsx` around line 645.

**P2-NEW-3 — Send button reaches WCAG 2.5.5 (44) but Close button sits at 40.**
Spec-wise, Close at 40×40 is fine for WCAG AA / Material guidance, but WCAG 2.5.5 Level AAA asks for 44 minimum. Bumping `closeButton.width/height` to 44 in the styles object would put both interactive controls at the same AAA bar. Trivial change.

**P2-NEW-4 — Tab from page body to FAB does not focus FAB on first press (in this Chrome session).**
After Escape, focusing the body via `.blur()` then pressing Tab did not advance focus to the FAB. Could be a chrome-devtools artefact (sequential Tab events from a detached body element), but worth a manual recheck with a real keyboard. Not blocking and not reproducible enough to log as P1.

## Three Things That Now Land Especially Well in R2

1. **Honest error state.** The new red ✕ + "We couldn't send your feedback right now." + Retry button is exactly the right pattern. Users instantly know it failed (color + icon + sentence all reinforce), Retry is the primary CTA, Close is secondary. A bouncer would now give this dimension a full 10/10 vs. the R1 fake-success.
2. **Complete dialog semantics.** Going from "just a div" in R1 to `dialog "Send feedback" description="..." modal` in R2 means VoiceOver, NVDA, JAWS, and TalkBack will all announce the dialog opening with both its title and a one-sentence description. Combined with the focus trap and Escape-to-close, screen-reader keyboard users now have a first-class flow.
3. **Stable touch targets.** Send at 44px exactly matches the WCAG 2.5.5 line; Screenshot at 44 too; Close at 40 is comfortable on mobile. R1's 19×29 close button was a clear mistap target on a thumb-driven phone; R2's 40×40 is solid.
