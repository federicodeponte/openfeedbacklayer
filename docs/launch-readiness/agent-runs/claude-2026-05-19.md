## Findings (Severity-Ordered)

### P0 (blocks ship)

**None.** The widget submits feedback successfully across viewports, returns sensible AI classifications, handles empty-message and no-email cases correctly, and does not crash on a 5000-char payload.

### P1 (polish — fix before broad launch)

**P1-1 — Geist font 403, page falls back to Times New Roman**
The host page requests `/__nextjs_font/geist-latin.woff2` which returns **403 Forbidden** twice during the session. Result: `document.body` `font-family` resolves to `"Times New Roman"`. This is a Next.js font-pipeline misconfiguration. The widget itself uses `system-ui, -apple-system, sans-serif` so it looks OK, but the example page heading is in a mono fallback and the body copy is in Times Roman, which makes the whole demo look broken.
Repro: load the URL, open DevTools Network, filter font, see `geist-latin.woff2 — 403`.
Screenshot: `/tmp/lr-claude-01-desktop-home.png`

**P1-2 — Escape key does NOT close the popup**
Pressing Escape (dispatched on `document`, `window`, and the focused element) leaves the widget open. This is a standard expectation for any dismissible popover.
Repro: open widget, press Escape — widget remains visible.

**P1-3 — Focus is not returned to the FAB after close**
After clicking the × button or Close button, `document.activeElement` is `<body>`, not the trigger FAB. Screen-reader and keyboard users lose their place.
Repro: tab to FAB → Enter → fill → Send → Close. Focus is on body.

**P1-4 — No `role="dialog"`, no `aria-modal`, no focus trap**
The popup is just a `<div>` — screen readers will not announce "dialog opened", users can tab out of the popup into the page behind it (which has no other interactive elements here, so it's invisible to the eye, but still wrong).
Repro: `evaluate_script` — `document.querySelector('[role="dialog"]')` returns null, ditto `[aria-modal]`.

**P1-5 — Close button has no accessible name**
The `×` button (uid 14_1) renders the literal character `×` with no `aria-label`. Screen readers read this as "multiplication sign" or similar. Should be `aria-label="Close feedback"`.
Repro: inspection — `closeBtn.getAttribute('aria-label')` returns `null`.

**P1-6 — Close button touch target is 19x29px (well below 44px)**
The × close button is 19px wide × 29px tall. Apple HIG / WCAG 2.5.5 ask for 44x44 minimum. Easy mistap on mobile.
Repro: inspection — `closeBtn.offsetWidth=19, offsetHeight=29`.

**P1-7 — FAB lacks `aria-expanded`, `aria-haspopup`, `aria-controls`**
The FAB button toggles a popover but does not advertise that to assistive tech.
Repro: inspection — all three attributes are `null` on the FAB.

**P1-8 — Form fields missing `id` and `name` attributes**
Chrome's a11y panel raises "A form field element should have an id or name attribute" (count 9 after the full session). Autofill and screen readers depend on these.
Repro: `list_console_messages` includes the issue.

**P1-9 — Close (×) button has `type="submit"` and lives outside a `<form>`**
The × button has `type="submit"` but there is no `<form>` wrapper. The Send button also has `type="submit"` but no form. No native form submission semantics, so Enter-in-textbox doesn't submit and there's no degraded JS-off behaviour. It also means the close × theoretically could trigger an unintended submit if a form ever got added around it. Cosmetic but fragile.

### P2 (nice to have)

**P2-1 — HMR WebSocket noise in console**
`ws://65.21.90.216:3025/_next/webpack-hmr` fails on every load. This is the dev server's hot-reload socket; in a production build it would not exist. If this URL is the public preview, run `next build && next start` instead of `next dev` to remove these.

**P2-2 — Send button height 36px is below the 44px touch guideline**
Send is 140x36. Width is fine, height is a hair short. Mobile mistap risk is low because of the comfortable horizontal target.

**P2-3 — Color of FAB button text is `rgb(0, 0, 0)` by default**
The SVG icon overrides with `stroke="white"`, so this is harmless. But if a future contributor adds text to the FAB, they will get black-on-blue (contrast ratio ~3.7, fails AA). Set `color: #fff` on the button explicitly.

**P2-4 — Email line wrapping on mobile uses a hard hyphen-break**
On the mobile success state, the email `depontefede+lr-claude-mobile@gmail.com` wraps mid-token (after `+lr-`). Looks OK but a `word-break: break-all` or `overflow-wrap: anywhere` would feel more intentional than a hyphen-split.
Screenshot: `/tmp/lr-claude-08-mobile-success.png`

**P2-5 — No visible character counter for the textarea**
Pasting 5000 chars works fine, but the user has no idea if there's a limit. A simple `Math.max(0, 5000 - value.length)` counter under the textarea would help.

## Three Things That Work Especially Well

1. **AI summarisation + classification is the killer feature.** The success state shows a polite, human-readable rewrite of the user's complaint plus three badges (category / feature-area / priority). My "Demo test from launch-readiness — please ignore" came back as "User has submitted a test entry for launch-readiness and requests it be ignored" with badges `other / launch-readiness / P2`. The 5000-char Lorem Ipsum came back with "The user has provided a large amount of placeholder text, which does not contain actionable feedback" plus two clarifying questions — sensible, not naive. This is the moment a virgin user goes "oh, this is different".
2. **Empty-state handling is correct everywhere.** Send is disabled until message is non-empty (no nag dialog, no alert). Email is genuinely optional — the success state shows the "We'll email you..." line only when email is provided. The subscribe checkbox starts disabled and auto-checks when email is entered. This is small but a lot of widgets get it wrong.
3. **No layout pollution at any viewport.** The popup is `position: fixed; bottom: 20px; right: 20px; z-index: 99999` with a soft `0 8px 32px rgba(0,0,0,0.2)` shadow and 12px border radius. At 375px, 768px, 1280px it stays anchored, never overflows the viewport, the textarea scrolls internally on big content rather than growing the card. POST is multipart/form-data with a `website` honeypot field — solid anti-spam baseline. No console hydration errors, no React strict-mode warnings, no source-map fails.
