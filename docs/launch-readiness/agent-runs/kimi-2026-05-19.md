## 3–5 P1 Polish Gaps (with exact evidence)

### 1. Install DX: Manual file copy is a friction cliff
> **Evidence:** README step 3 says `cp node_modules/openfeedbacklayer/src/api/feedback/route.ts app/api/feedback/route.ts`.  
> The `files` array in `package.json` includes `"src"`, so this *works*, but requiring users to `cp` from `node_modules` is brittle (path changes break on upgrade, users must know their framework's route convention). A CLI scaffold (`npx openfeedbacklayer init`) or at least documented `curl` templates would eliminate this. The `src/api/feedback/route.ts` file itself imports `NextRequest` — it's Next.js-coupled with no mention of how to adapt for Remix, SvelteKit, or raw Node.

### 2. `FeedbackDeps.supabase: any` undermines the entire type contract
> **Evidence:** `src/server/feedback-core.ts` line 10: `supabase: any`.  
> The server core's primary dependency is typed as `any`. This means zero IntelliSense for `.from('feedback').insert(...)`, no compile-time safety on table/column names, and no protection against API drift. For a package that asks users to wire server-side handlers, this is a significant API-contract hole. The `tsconfig.json` has `strict: true`, yet the most critical server interface opts out.

### 3. Widget shows "Thank you for your feedback!" even on total failure
> **Evidence:** `src/components/FeedbackWidget.tsx` lines 194–207.  
> In the `catch` block, the widget sets `isSent = true` and displays `aiResponse = 'Thank you for your feedback!'` regardless of whether the POST actually succeeded. The `onError` callback fires, but the UI lies to the user. A user who just lost their carefully-typed bug report sees a green checkmark. The `console.error` is invisible to non-dev users. This is a trust-destroying UX bug.

### 4. Rate limiter is in-memory and non-distributed with a documented but unmitigated spoofing risk
> **Evidence:** `src/server/feedback-core.ts` lines 40–48 and 46–69.  
> The code includes an admirably honest security comment: *"x-forwarded-for / x-real-ip are client-supplied... an attacker can rotate the header to bypass the cap"*. However, the mitigation is "deploy behind a trusted proxy" — there is no runtime enforcement or warning. On Vercel (the implied target), this is fine; on a self-hosted Node server, it's trivially bypassable. More critically, the `rateLimitMap` is a process-local `Map` — it resets on every cold start and does not coordinate across serverless instances. A determined spammer can hit 10 requests per instance per minute, multiplied by however many Vercel regions spin up.

### 5. Public Supabase Storage bucket with no size validation server-side
> **Evidence:** `supabase/migrations/003_screenshot_storage.sql` lines 20–26:  
> `CREATE POLICY "Allow public uploads to feedback bucket" ON storage.objects FOR INSERT WITH CHECK (bucket_id = 'feedback');`  
> The bucket has a 5MB `file_size_limit`, but the widget's client-side check (`file.size > 5 * 1024 * 1024`) can be bypassed by forging the request. The server (`feedback-core.ts` lines 150–170) does upload the file but never validates `screenshot.size` against a server-side limit before calling Supabase. The `contentType` is hardcoded to `'image/png'` regardless of actual file type — a bypassed JPEG/WebP gets mislabeled.

## 2–3 Things That Genuinely Work Well

### 1. The GitHub issue redaction pipeline is impressively thorough
> **Evidence:** `src/lib/github-service.ts` lines 27–207.  
> The redaction system shows real security craftsmanship: NFKC normalization, bounded quantifiers (ReDoS defense), Unicode-aware email/phone regexes with `/u` and `\p{L}\p{M}\p{N}`, control-character stripping, markdown defanging with zero-width spaces, URL sanitization with high-entropy path detection, and explicit comments explaining *why* each step exists. The `UNSAFE_URL` fallback and the honest disclaimer *"best-effort defense-in-depth, not a guarantee"* show mature security communication.

### 2. Atomic stage-claim RPC with proper privilege revocation
> **Evidence:** `supabase/migrations/004_claim_stage_rpc.sql` lines 30–66.  
> The webhook journey uses a PostgreSQL function with `IS DISTINCT FROM` for NULL-safe comparison, forward-only rank checking, and `RETURNING` for atomic claim semantics. The migration explicitly revokes `EXECUTE` from `PUBLIC`, `anon`, and `authenticated`, then grants only to `service_role`. This is exactly how you should build a concurrent-safe, least-privilege webhook handler. The inline comment even explains the prior bug (PostgREST rejecting `or` on mutation).

### 3. Graceful AI degradation with structured fallback
> **Evidence:** `src/lib/ai-service.ts` lines 19–27 and 121–124; `src/components/FeedbackWidget.tsx` lines 166–180.  
> If Gemini fails, returns garbage, or the key is missing, the system falls back to a default classification (`category: 'feedback'`, `priority: 'P1'`) instead of crashing. The server returns `ai_data: null` cleanly, and the widget handles it without throwing. This "AI is optional" posture is the right default for a feedback widget — users should never lose their submission because an LLM hiccuped.

## Honest Summary

OpenFeedbackLayer is a **competent, security-conscious package** with a genuinely well-built redaction and journey pipeline. The GitHub webhook flow and atomic stage claiming show real engineering care. However, it ships with **friction-heavy install DX** (manual file copies), a **type-system hole at its server core** (`supabase: any`), and a **widget that lies to users on failure**. These are fixable, but they are real barriers to adoption and trust. The security hygiene is above average for an open-source widget, but the operational gaps (in-memory rate limiting, no server-side upload size enforcement) mean it's not production-hardened out of the box.
